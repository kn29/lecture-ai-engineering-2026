## 宿題

### 1. 基礎

#### やったこと

| 項目 | 内容 |
|---|---|
| 同じ質問の比較 | 「LoRAとは何ですか？」を3つのモデルで実行し、回答の違いを比較した。モデル変更は `AIE_MODEL` 環境変数で行った。 |
| 実行コマンド | `AIE_MODEL=gemini-3.5-flash-lite uv run python -m app.ask "LoRAとは何ですか？"` / `AIE_MODEL=gemini-3.5-flash uv run python -m app.ask "LoRAとは何ですか？"` / `AIE_MODEL=gemini-3.8-flash uv run python -m app.ask "LoRAとは何ですか？"` |

#### 結果

##### モデル比較

| モデル | 入力トークン数 | 出力トークン数 | 解説 |
|---|---:|---:|---|
| `gemini-3.5-flash-lite` | 7 | 614 | 「Low-Rank Adaptation」の意味と、低コスト・省メモリ・小さな差分で学習する説明が中心。平易で初心者向け。 |
| `gemini-3.5-flash` | 7 | 742 | 背景、仕組み、メリット、用途まで丁寧に構造化されていた。技術理解を深めるのに適している。 |
| `gemini-3.8-flash` | 7 | 639 | 「AI技術」のLoRAだけでなく、通信技術のLoRa/LoRaWANにも言及し、文脈依存の意味の違いを説明していた。 |

- 共通点: 3つとも「LoRAはAIの重み全体を再学習するのではなく、差分だけを効率的に追加する技術」という中心概念は一致していた。
- 相違点: モデルごとに強調する観点が違い、`flash-lite` は簡潔、`3.5-flash` は構造化、`3.8-flash` は文脈の多様性を踏まえた説明となっていた。

##### temperature 比較

| temperature | 入力トークン数 | 出力トークン数 | 観察 |
|---|---:|---:|---|
| 0.0 | 7 | 644 | 最も安定した説明。要点が整理され、定義・メリット・背景が簡潔に示されていた。 |
| 0.7 | 7 | 753 | 例え話や具体例が増え、説明の豊かさが増した。理解には優しいがやや冗長。 |
| 1.2 | 7 | 687 | 表現が広がり、比較やイメージを含んだ説明になったが、要点がやや散りやすい。 |

- まとめ: temperature を高くすると言い回しや具体例が豊かになる一方、安定性と簡潔さは下がる。逆に低い値は要点が強く出て、説明の再現性が高い。

#### 気づき・疑問

- 同じ質問でも、モデルが変わると説明の粒度や強調点が変わることを確認できた。特に出力トークン数は `gemini-3.5-flash` で最も多く、説明が最も詳しかった。
- 入力トークン数は全モデルで 7 でほぼ同じなのに、出力サイズは大きく異なっている。これはモデルの出力スタイルや推論方針の違いによると考えられる。
- `3.8-flash` は「LoRA」の別意味（通信技術）にも触れており、文脈が違えば答え方が大きく変わることが分かった。
- `generate_content` の `config` に `temperature` を入れると、回答の多様性や冗長さが実際に変化することを確認できた。これは同じ質問でも出力の「安定性」と「創造性」を調整できる重要な設定だと感じた。
- 温度が高いと説明の幅が広がる一方で、低い温度の方が要点を短く伝えやすい。用途に応じて、`温度=0.0 〜 0.7` で安定、`0.7 〜 1.2` で創造性を重視するのが実用的だと考えられる。
- 疑問: 実際のアプリでは、temperature を低くして正確さを優先するのか、やや高くして柔軟な表現を求めるのかを、ユースケースごとに切り分ける必要があるのではないか。

### 2. 実装

#### やったこと

| 項目 | 内容 |
|---|---|
| 課題の指示 | `app/ask.py` を改修し、会話履歴を保ったまま続けて質問できるようにする |
| 実装した対応 | `genai.Client` をモジュール変数 `_CLIENT` として保持し、`get_client()` で再利用するようにした。 |
| セッション管理 | `get_chat_session()` で `_CHAT_SESSION` を作成し、同じセッションを再利用するようにした。 |
| 実際の動作 | `ask(question)` は毎回 `chat.send_message(question)` を呼ぶが、前の会話がセッションに残るようになっている。 |
| 根本原因 | 関数内で `client = genai.Client(...)` を作っていたが、関数のスコープを抜けると内部の HTTP クライアントが閉じられてしまう。 |

#### 検証例

```python
import app.ask as ask_mod

ask_mod._CLIENT = None
ask_mod._CHAT_SESSION = None

q1 = 'LoRAとは何ですか？'
a1 = ask_mod.ask(q1)

q2 = '先ほどの説明を、1文で簡潔に言い換えて'
a2 = ask_mod.ask(q2)
```

#### 結果

| 検証項目 | 確認結果 |
|---|---|
| 1回目の質問 | 正常に返答された |
| 2回目の質問 | `chat.send_message` が呼ばれ、前の説明を踏まえた要約が返ってきた |
| 履歴保持の証拠 | 2回目の入力トークン数が大きく増加し、履歴が含まれていることを確認できた |
| 実測値 | 1回目: `[入力トークン数] 7`, `[出力トークン数] 637` / 2回目: `[入力トークン数] 659`, `[出力トークン数] 46` |
| 追加確認 | `client_exists = True` / `chat_exists = True` を確認し、同じセッションが維持されている状態であることを確認した |

- 2回目の入力トークン数が大きく増えたのは、前の発話が履歴として含まれたためであり、継続会話が実際に機能していたと判断できる。
- 追加で `client_exists = True` / `chat_exists = True` も確認し、同じセッションが維持されている状態であることを確認した。

#### 気づき・疑問

- 実際の検証の進め方として、まず `ask()` を1回だけ呼ぶ確認を行ったが、これでは会話履歴の継続が正常に動いているかは分からない。
- そのため、2回連続で質問する具体例を用意して、2回目の `prompt_token_count` の増加と、前の説明を踏まえた返答が出るかを確認した。
- ここで重要だったのは、`client` と `chat` の両方が保持されているかを確かめることだった。最初の検証では `chat` だけを保持している前提で確認していたが、実際には内部の GenAI クライアントも閉じられていた。
- 追加の具体例で検証したときに `RuntimeError: Cannot send a request, as the client has been closed.` が出た。これは、チャット履歴だけではなく、下位の HTTP クライアントのライフサイクルも管理する必要があることを示していた。
- つまり、会話履歴の維持は「チャットオブジェクトを再利用する」だけでなく、「クライアント自体を生きた状態で保持する」ことが前提であると分かった。

### 3. 発展

#### やったこと

| 項目 | 内容 |
|---|---|
| 課題の指示 | 応答時間とトークン数を計測し、複数のモデルや質問で比較する。無料枠のレート制限との関係も考察する |
| 実装した対応 | `measure_response(model_name, question, temperature=None)` を `app/ask.py` に追加した。 |
| 計測方法 | `time.perf_counter()` で開始・終了時刻を取得し、`client.models.generate_content(...)` の実行時間を計測した。 |
| トークン取得 | `usage_metadata` から `prompt_token_count` と `candidates_token_count` を拾い、`total_tokens` を計算した。 |
| 比較のしやすさ | 辞書形式で結果を返すようにし、複数モデルと複数質問の比較をしやすくした。 |
| 拡張 | `temperature` を指定して、モデルや温度が応答時間とトークン数にどう影響するかも比較できるようにした。 |

#### 結果

| モデル | 質問 | 応答時間 (秒) | 入力トークン数 | 出力トークン数 | 合計トークン数 |
|---|---|---:|---:|---:|---:|
| `gemini-3.5-flash-lite` | `LoRAとは何ですか？` | 2.86 | 7 | 612 | 619 |
| `gemini-3.5-flash-lite` | `AIE2026の講座の宿題にある「3レベル」とは何ですか？` | 2.35 | 21 | 512 | 533 |
| `gemini-3.5-flash` | `LoRAとは何ですか？` | 13.352 | 7 | 749 | 756 |
| `gemini-3.5-flash` | `AIE2026の講座の宿題にある「3レベル」とは何ですか？` | 11.86 | 21 | 612 | 633 |
| `gemini-3.8-flash` | `LoRAとは何ですか？` | 78.721 | 7 | 729 | 736 |
| `gemini-3.8-flash` | `AIE2026の講座の宿題にある「3レベル」とは何ですか？` | 65.154 | 21 | 716 | 737 |

- 比較のまとめ:
  - 同じ質問でも、より高性能な `gemini-3.5-flash` は `flash-lite` よりも遅く、出力トークン数も多い。
  - `gemini-3.8-flash` はさらに長い応答時間と大きな出力を示し、最も高い応答品質とコストを伴うモデル群であることが分かった。
  - 出力トークン数は質問内容の違いによる影響も見られた。今回の実測では、`gemini-3.5-flash` で `LoRAとは何ですか？` の出力トークン数は 749、`AIE2026の講座の宿題にある「3レベル」とは何ですか？` は 612 であり、固有質問の方が出力トークン数は小さくなっている。
  - 無料枠では、API側が「一定時間内に使える量」を制限しているため、1回ごとの応答が積み重なると制限に達しやすくなる。これは単に「出力が長い」だけでなく、短時間に何度も呼び出すことや、より高性能なモデルで処理時間が長くなることが重なると起きやすい。実務上は、1回のリクエストの大きさだけでなく、実行頻度と連続実行時間も前提条件として重要である。エラーコード 429 は「リクエスト数が多すぎる」、503 は「一時的にサービスが混雑している」ことを意味し、無料枠ではこのような制限にぶつかることがある。
  - つまり、モデルが速いほど安価であるとは限らず、予算やレート制限を考えると、出力品質と応答速度の両方を踏まえて最適なモデルを選ぶ必要がある。

#### 気づき・疑問

- 応答時間の比較では、`flash-lite` は `flash` よりも早く、また出力トークン数も少なかった。これは応答速度と品質のトレードオフに見える。
- さらに、`gemini-3.8-flash` は `3.5-flash` よりも明確に応答時間と出力トークン数が増え、より重い推論処理が行われていると考えられる。これは、最も高性能な回答の一方で、無料枠のコストと速度の両方が大きくなることを意味する。
- ただし、品質が要るときには `flash` や `3.8-flash` の方が十分に有効で、質問が入門的なものであれば `flash-lite` の方がコスト効率が良いと感じた。
- 無料枠のレート制限との関係では、数回の比較では問題にならなくても、短時間に大量の問い合わせを繰り返すと 429 や 503 が発生しやすい。特に `3.8-flash` のような応答の重いモデルは、同じ時間当たりの利用量が大きくなりやすく、無料枠管理の観点では慎重な運用が必要だと感じた。
- 疑問: 実運用では、質問の文字数や文脈の量がどの程度コストと応答時間に影響するのかを、モデルごとに定量的に整理しておくと設計しやすいのではないか。

## まとめ

- 基礎では、モデルと temperature の違いが回答の安定性と豊かさに大きく影響することを確認した。
- 実装では、会話履歴を維持するにはクライアントとチャットセッションの両方を保持することが重要であることを実際の検証で確認した。
- 発展では、応答時間とトークン数を定量的に比較できるようになり、モデル選択と利用コストのバランスを議論できるようになった。
- これらの結果から、AIを実運用で使う際には、精度だけでなく速度、コスト、レート制限、文脈保持の観点を総合的に考える必要があると感じた。
